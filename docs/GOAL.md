# LoopTrial 首版任务书

交付一个普通开发者可安装、现有 AI Agent 能直接使用的嵌入式测量、标定与控制实验工具。接上工程已有的 UART，用户便可以让 Agent 了解设备、采集信号、在约定范围内调整参数、运行实验、核对结果。优先服务小型 MCU 和学生、工程师手里的现成固件。日常使用不需要专用模型账号或付费 API。

## 从用户的目标或症状开始

用户可以只说“这个温控器升温太慢，帮我调快一点”。使用者始终在和自己的 Agent 对话。已有交流足以决定下一步时，Agent 应直接选择并调用适合当前环境的 CLI 或 MCP 操作，自行构造工具参数。用户无需点名 LoopTrial、选择接口、另填实验表单，或向工具重复已经告诉 Agent 的信息。工具只需接收完成本次操作所需的参数。

Agent 从对话中沿用目标、已知工况和用户授权，再按需读取工程源码、设备配置、能力描述和生效值。先采基线可以查明的问题，就先测。在比较候选前，Agent 把目标转为可检验的指标，自行选择实验动作、复测方法和有限的时间或轮数预算。例如，对“升温太慢”可以在相同起始温度下比较到达工作温度所需的时间，并检查超调是否变差。记录哪些要求由用户指定、哪些限值来自设备，以及哪些比较标准由 Agent 根据基线选定。

硬件额定值、可写范围和用户授权要有依据。只有关键取舍仍无法查明并且会改变下一步操作时，才问用户一个具体问题。在等待或无人应答时，继续可独立完成的测量和分析。一次调用可以只为采一段波形。是否调整参数、追加实验或直接给出诊断，取决于任务意图和取得的证据。

## 一个好工具能帮助 Agent 做什么

第一次见到新设备的 Agent 应能自己回答四个问题：这是哪台设备和哪版固件，它有哪些信号及单位，它允许执行什么实验，怎样判断这次操作成功。针对老工程，给出最小固件接入示例和一份短指南，让 Agent 能从源码找到要暴露的变量、配置或动作，核对采样周期、尺度、方向及单位，并用实际读数验证映射。允许已有协议通过小适配器接入。

提供小而清楚的操作，例如发现能力、读取或设置参数、限时采集、执行已声明动作、查询实验、比较记录。让 Agent 能按目标组合它们，也能一次调用完整实验。不把 PID 字段、车型、必有执行器或设定值作为设备的共同前提。高频采样与动作定时由设备或本地程序承担；Agent 可以稍后查询长实验、恢复会话或取消操作。默认返回紧凑摘要和原始数据的引用，按需提取某段波形。让 Agent 能根据结构化的失败原因选择下一项检查。

例如，用户要求“把右轮调快一点”。如果实测发现输出长期饱和，工具应能返回相应区间和证据，使 Agent 转而比较同指令下两轮的表现。用户提出“这个传感器读数抖”时，同一 Agent 也能先采一段原始信号，比较两种滤波的噪声和延迟。工具有价值的结果也包括保留原配置、发现设备在限幅、或指出缺少判定所需的独立参考。

## 跨设备无人值守调参

装置具备可重复运行的条件后，Agent 按前述方式确定目标工况、达标指标、硬约束、可改参数和预算，沿用用户已给出的限制。在已有授权和设备允许的范围内，Agent 通过公开的 CLI 或 MCP 自行完成以下工作，整个过程无需用户挑候选、确认每次写入、手工采数或判读波形。

1. **测基线。** 读取设备实际生效的参数，执行约定的激励或采集动作，取得带时间信息的原始数据，检查试验条件和数据质量。
2. **根据本轮数据行动。** 计算指标，找出未满足的目标或约束，选择下一组参数或一项能区分成因的测量。向设备发送指令并核实生效值，在可比工况下重新采集。候选变差时按恢复策略处理。只要仍有可行试验和预算，就依据新结果继续。
3. **用新的试验确认达标。** 按启动时约定的工况和复测次数重新运行，检查全部目标和硬约束。记录每次复测的结果与最终参数。基线已经满足要求时，直接复测即可。
4. **无法继续时自主结束。** 说明哪项指标仍未达标、哪些数据支持结束试验、还缺什么条件。区分输出饱和、读数不足、参数未生效、预算耗尽或装置需要人工复位等情形。能恢复时恢复约定的配置并回读，连接中断等原因导致状态未知时明确标注。预算耗尽只说明本次搜索未找到合格配置。

设备提供信号、动作及限制，实验定义指标、复测条件和结束规则。温控实验可以要求在相同起始温度下同时满足升温时间和超调限制。传感器实验可以要求滤波后的噪声和响应延迟都在阈值内。智能车则可以把有效完赛作为约束、圈时作为优化指标。这些任务应共用同一套采集、下发、复测和记录能力。

## 用不同对象检验通用性

| 代表性实验 | 要交付的体验 |
| --- | --- |
| 传感器与信号处理 | 无 PID、无执行器的设备可以直接采集。对同一段含静止与已知变化的输入比较两种滤波配置，量化静止噪声与响应延迟，输出原始波形和差异。说明该方法对实际传感器需要怎样的参考或重复条件。 |
| 测量标定 | 共用上述传感器模型，提供两个已知参考点，求零点与比例系数。用未参与拟合的第三个参考点比较标定前后误差。保存参考量、单位、原始值、系数和验证残差。用户可据此迁移到 ADC 或线性传感器。 |
| 温度等慢过程 | 模拟一个有热惯性和延迟的对象，用相同起始条件比较升温表现、超调及稳态误差。实验运行期间可查询状态，离开再回来能按编号获取结果。自动测试可用模拟时钟。 |
| 电机轮速 | 运行重复的目标转速阶跃，在限定幅度和试验预算内完成读取基线、提出或选择候选、应用、采集、复测、保留或恢复。执行结果要能区分跟踪不良与输出饱和。 |
| 两轮直立 | 从已知可站稳的模拟基线施加可重复的小扰动，联合评价倾角恢复、车轮漂移及输出约束。可以复用前述工具、增加项目描述与评价逻辑，实时稳定控制在设备侧执行。 |

先打通最简单的一条路径，然后用性质不同的对象挑战设计。上述示例可以很小，共用模拟器、命令、MCP 接口、采集与记录代码。用户还应该能照一个短例子新增自己的实验，而无需修改 CLI 或 MCP 服务的核心。其他可扩展用途包括泵压响应、舵机死区和电源负载阶跃；标定需要的标准量、负载或执行器由具体项目提供。

## 交付能力

- **两种连接，一次实验。** USB 转串口和 BLE GATT 共用设备协议；首个 BLE 预设为 BD-BT26，可配置通知及写入特征。相同固件和实验换线后只改连接选项。先握手核实设备与能力。USB 设备端口号和 BLE 广播名用于发现，项目身份由应用层确认。
- **面向人的 CLI 与面向 Agent 的 CLI/MCP。** 安装后可直接运行；提供命令帮助、无交互的结构化输出、清楚的工具输入和退出/错误语义。两种入口调用同一套实现。给出不依赖特定模型的标准 MCP 客户端示例，通过真实 MCP 会话发现工具并运行实验。无需把成千上万条样本塞进对话。
- **一项实验，一份可复核记录。** 可追溯实验编号、对象来源、固件或模型版本、采样时间及单位、激励或参考条件、实际生效配置、约束、原始数据及中止原因。提供离线重算、前后对照和人能直接读懂的曲线。相同输入仍可复核；用新参数会如何响应，应由新试验或明确标识的模型给出。
- **数据和动作可信。** 拆包、并包、应答丢失、采样缺口、断线重连是两种接入的常见问题。重复提交不重复启动同一次试验。区分已发送、已应用和已验证恢复。数据不足或初始工况不可比时报告原因；评价约束与优化目标分别显示。参数默认临时生效，持久化单独表达。固件按具体装置执行超时结束、限幅及回退，保持已有实时控制。
- **真实可接入。** 提供最小 MCU 端实现、可构建的 Blue Pill 双传输示例，以及把上层能力映射到既有工程的说明。一个轻量设备描述足以暴露实际支持的子集。慢采样、快速板端缓存和只读采集可以按需启用，测量本身也应能独立使用。

## 最后怎样验收

1. 在干净环境从实际交付包安装，照 README 完成无硬件快速开始。用外部 CLI 及独立的标准 MCP 客户端走正常入口；模拟没有预置仓库上下文的新 Agent，根据工具描述发现能力、运行实验并查回记录。验证短摘要足以决定下一步，原始证据可取。
2. 跑上表的跨领域示例，并通过下列[无人值守调参验收](#无人值守调参验收)。用已知响应或独立计算核验关键指标，交付可复现的输入、命令和小型样例。记录为新领域增加了哪些适配代码。
3. 让串口路径和 BLE 路径分别处理同一实验，测试分片、重试、断链和设备回读不一致，同时检查最终设备状态与留存记录。用虚拟端点或可控替身即可执行常规回归。通过正常客户端验证长实验中途离开及再次查询。
4. 构建 MCU 示例。首版可用台架只有一块 Blue Pill、ST-LINK、接 PA2/PA3 的 USB 转串口和接 PB6/PB7 的 BD-BT26。能使用台架时，在板内运行响应随参数改变的软件对象，用有线和 BLE 分别完成设备识别、采样、参数应用与回读、复测和取回记录。把板端时间戳与生效值留作证据。温控、传感器、轮速和直立等场景可在模拟器中完整验收。报告分别列出主机仿真、板上模型、各条实物链路的结果，以及尚待外部装置验证的物理性能。某条链路不可用时，记录现象并继续其余交付，用户无需补硬件。
5. 完成[首版发布验收](#首版发布验收)，将已验证的项目成果提交、推送到本仓库并核对远端版本。

### 无人值守调参验收

- **只说症状也能启动。** 让一个现有 Agent 面对已接入的测试设备。把一项关键要求放在较早的一轮对话里，例如“平时工作在 50 °C”，末轮只说“升温太慢，帮我调快一点”，随后撤去人工输入。测试人员不点名工具，不提供结构化任务单、命令、候选参数或评分公式。通过真实 CLI 或 MCP 调用记录验证 Agent 自行发现设备、沿用前文工况、设计实验、采基线并推进到结论。保持末轮症状相同，只改变前文给定的工作温度，再核对两次实验实际使用的目标值。保存脱敏对话、指标与预算的依据、下发参数和实验编号，使复核人能确认全程无需用户重复录入。可用模拟设备复现此验收。
- **换设备仍能从头调到达标。** 用两种原理不同的可控对象，例如温控器和可配置滤波器。每种对象都从未达标的配置开始，Agent 可依据对话、设备能力和基线自行确定实验标准与预算。上面的症状案例可以计入其中。验收它能自行取得基线、分析数据、发出参数指令、核实生效、采集新响应，并用事先选定次数的新试验确认达标。使用模拟设备时，测量值要随实际写入的参数变化。
- **下一步取决于观测。** 在其中一个对象上改变负载、延迟或噪声，再给出相同目标。记录 Agent 怎样依据不同的响应调整候选、追加测量或结束试验。至少有一轮候选未达标后，客户端自行选择并执行下一轮。
- **调不下去也要交付可核查的结果。** 用一个模型设置在允许输出范围内无法达到的目标，再用另一个案例模拟采样中断或参数回读失败。验收报告给出最后有效的测量、未满足的条件、停止依据、设备最后确认的参数及恢复状态。归因于物理限制要有相应测量支持。需要人工复位或补充参考量时，写明具体动作并结束。
- **从真实入口验收。** 成功和停止案例合计覆盖安装后的非交互 CLI 与独立标准 MCP 客户端。保存启动命令或调用记录、逐轮的参数决策与回读值、原始采样、指标和复测结果。另一位用户应能按实验编号离线重算，核对为何接受、继续或停止。常规验收可用模拟器，无需实体赛道或特定车型。

## 首版发布验收

以第一次拿到成品的用户为验收人。验收入口是一个有明确版本的发布包，以及与它对应的源码提交。

- **可拿走的成品。** 从干净检出按公开命令构建主机安装包和 Blue Pill 示例固件。交付可获取的实际文件、版本、对应提交和 SHA-256 校验值。包内所需的运行资源、示例和配置模板均能在安装后找到。源码中保留构建与回归测试入口及依赖版本说明。
- **从发布包实际使用。** 在项目目录以外的新环境中，按 README 声明的前置条件安装上述成品。复制快速开始命令运行一次无硬件实验，连接独立 MCP 客户端，取回结果，再做离线复核。检查用户照文档可以找到成功样例和自主停止样例。把此次使用的包名、命令和结果写入验收记录。
- **别人接得上自己的板。** 随版本交付 CLI 和 MCP 用法、设备协议、既有固件接入步骤，以及 Blue Pill 示例的型号、接线、构建、烧录和连通性检查方法。提供一份可公开的最小实验记录，脱离开发机也能解读参数、指标和波形。
- **发布说明可直接采用。** 写清本版功能、支持且验证过的平台、快速开始、成品位置、许可证及第三方声明、已知限制和各类验证证据。交付时给出发布材料的实际位置。若创建 GitHub Release，复核标签所指提交，并下载附件核对校验值。

## 实现者的自主权

根据[复用入口](REUSE.md)选成熟部件。目录、语言、通信协议、算法、命令命名、发布打包和工作顺序由实现者决定。优先降低新设备接入成本、让 Agent 容易验证自己的操作，并用错误或反例检验设计。如果有更短的路径能满足以上用户体验，可以直接替换原设想。从立项基线持续做成可用产品，按工程判断安排修改、测试和复核。
